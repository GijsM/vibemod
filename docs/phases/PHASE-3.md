# Phase 3 brief — the Registry.register seam: real items and entity types at runtime

Prerequisites: `PHASE-0/1/2-RESULT.md` (surgeon+shims, command seam, client entrypoint/keybind/HUD seams, resources channel + respack + ReloadCoordinator all exist and are gated). Same hard constraints; all gates grow, never weaken — current: build (surgeonSelfTest 38 + store/prompt asserts), smoke-fabric 75/75, smoke-neoforge 44/44, client gate 79/79.

## Goal

A generated mod registers a **real item** the way every Fabric mod does — `Registry.register(BuiltInRegistries.ITEM, Identifier.of("ns","ruby"), new Item(new Item.Properties()))` (or an `Item`/`SwordItem` subclass) — and it works in the live singleplayer/LAN-host game: in a creative tab, craftable via the mod's `data/**` recipe, textured via its `assets/**`, holdable, usable. Disable/unload tombstones it cleanly; reboots are stable. Entity types similarly (spawnable via the mod's own code/commands, with default attributes). No new mod-facing API.

## Verified 26.2 facts (javap'd; re-verify what you wire)

- `MappedRegistry`: `private boolean frozen`; `public Registry<T> freeze()`; only register overload `register(ResourceKey<T>, T, RegistrationInfo)` → an `@Accessor("frozen")` mixin (`MappedRegistryAccessor`, common — not client-only) is the unfreeze path. `Registry.register` statics: `(Registry<? super T>, String, T)`, `(Registry<V>, Identifier, T)`, `(Registry<V>, ResourceKey<V>, T)`, plus `registerForHolder` ×2 — seam **all five**.
- `BuiltInRegistries.ITEM/BLOCK/ENTITY_TYPE` are `DefaultedRegistry`s (still `MappedRegistry` subclasses — verify `DefaultedMappedRegistry` hierarchy with javap and target the right class for the accessor).
- Items in 26.2: verify with javap whether `Item.Properties` requires a registry key before construction (`setId`/`registryKey`-style — 1.21.2+ vanilla required `Item.Properties().setId(ResourceKey)`; check what 26.2 wants and wire the shim to inject the right key when the mod didn't). If item construction requires the id up front, the shim may need to intercept at register time with the mod's Properties-built item and fix up components — investigate `Item.<init>` / `Item.Properties` methods and vanilla `Items.register` helpers and mirror what vanilla does.
- Creative tabs: javap `CreativeModeTabs`/`CreativeModeTab` + `FabricItemGroupEvents` (`ItemGroupEvents.modifyEntriesEvent(ResourceKey<CreativeModeTab>)` — fabric-item-group-api-v1; verify exact 26.2 names). Runtime-added items likely need a rebuild of tab contents (`CreativeModeTabs.tryRebuildTabContents` or the current equivalent — javap it) after registration and after unload.
- Item models: 26.2 uses `assets/<ns>/items/<id>.json` item-model *definitions* plus `models/item/`. Unzip a vanilla item's files from the client jar (`~/.gradle/caches/fabric-loom/26.2/minecraft-client.jar`) and mirror the exact shape; the Phase 2 respack + reload pipeline delivers them.
- Entity types: `EntityType.Builder` (javap: `of(EntityFactory, MobCategory)`, `build(...)` — check whether build wants a `ResourceKey`), `FabricDefaultAttributeRegistry.register(EntityType, AttributeSupplier.Builder)` (fabric-object-builder-api — verify current name/pkg) — seam it or call the vanilla `DefaultAttributes` map accessor. Spawning needs no spawn-egg or worldgen; the mod spawns via its own code/commands.
- Registry sync: on singleplayer/integrated server, client and server share the registry objects → immediate visibility. Already-connected remote LAN guests and dedicated servers cannot receive new ids mid-session → **gate: on a dedicated server, `Registry.register` produces a clear surgeon/runtime diagnostic ("registry content is singleplayer/LAN-host only in v1; applies after restart on dedicated")**; verify what actually happens on the dedicated smoke (vanilla clients aren't connected there, so runtime registration may technically succeed — still refuse, deterministically, because a later-joining client would desync; the smoke asserts the refusal message).

## Deliverables

### A. Registry shim (`Shims.registryRegister`, fabric)
- Seam all five `Registry.register`/`registerForHolder` statics → `Shims`. Behavior:
  - Only `BuiltInRegistries.ITEM` and `ENTITY_TYPE` are supported in Phase 3. `BLOCK` → do the feasibility spike (blockstate registry, `Block.BLOCK_STATE_REGISTRY` id assignment, model/render layer): ship it only if a placed block renders and survives reload without client crashes in the gate; otherwise a clear diagnostic steering to items+`data/**` (record which in the result doc). Any other registry → clear diagnostic naming what is supported.
  - Namespace the id onto the mod's canonical `vibemod_<mod>` namespace (mirroring Phase 2's rule; if the model used its own ns the rewrite already happened in resources — keep code-side ids consistent by rewriting here too).
  - Unfreeze (accessor) → register (vanilla path with `RegistrationInfo`-correct call) → refreeze. Main thread only.
  - Ledger `<datadir>/registry-ledger.json`: mod → registered ids (+ registry). On re-register of a live mod at boot restore, same ids. Unloaded mods: never re-registered (tombstone — the id stays absent next boot; vanilla drops unknown ids from world saves; document). On disable (not unload): the entry stays registered (cannot remove) but its *behavior* is inert only insofar as the item object's callbacks do nothing — plain `Item`s have no callbacks; subclasses keep their code but their event/command registrations are drained. Record this honestly in docs/UI (`/vibe info` shows "registered content: …").
  - Creative tab: add to a sensible vanilla tab (e.g. search + a default) or a single "VibeMod" tab if runtime tab creation is viable (a tab is itself a registry entry — same shim path); rebuild tab contents after changes; verify client sees it.
- `describeState()` counts for gates. Kind.CONTENT tracking with the drain marking tab rebuild + ledger update via the coordinator (never synchronous heavy work in drain).

### B. Entity types
- `Shims.defaultAttributes` seam (or vanilla map injection) so `FabricDefaultAttributeRegistry.register` in mod init works; `EntityType` registration through the same registry shim; verify spawn (`EntityType.create(level, EntitySpawnReason...)` + `addFreshEntity`) works for a runtime-registered type with a vanilla-ish renderer fallback — **client rendering of a custom EntityType needs a registered renderer**, which is a client-registry problem: check `EntityRendererRegistry` (fabric-rendering) registration timing; if late registration is impossible, constrain the prompt: custom entity types extend vanilla mobs' types only for logic-side use, and visual mobs use a vanilla `EntityType` + equipment/scale (the classic approach) — decide by experiment in the client gate and record it.
